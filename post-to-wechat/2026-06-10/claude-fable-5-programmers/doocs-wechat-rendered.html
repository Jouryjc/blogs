这次 Claude 5 对程序员的意义，不是补全几行代码更快，而是可以尝试把以前不敢交给 AI 的长任务往外放。

比如跨几十万行代码的迁移、一个难复现 bug 的排查、带测试验证的重构、从产品截图还原前端实现、让 Agent 在仓库里跑一段时间再回来交付结果。

准确地说，Anthropic 这次发布的是 Claude Fable 5 和受限访问的 Claude Mythos 5。普通开发者真正会用到的是 Fable 5。Mythos 5 更像同一能力层级的受控版本，主要给 Project Glasswing 等安全和科研合作方。

WECHATIMGPH_1

如果只看发布会词汇，很容易把它理解成“又一个更聪明的模型”。但从程序员视角看，Fable 5 的变化更具体：它把 AI 编程的任务单位，从“写一段代码”推向“接一个工程任务”。

先校准一个名字：这不是 Sonnet 5

很多人看到“Claude 5”会自然想到 Sonnet 5、Opus 5。官方这次没有这么命名。

公开可用的模型叫 Claude Fable 5，API ID 是 claude-fable-5。Anthropic 把它放在 Mythos-class 里，也就是高于 Opus class 的能力层级。Claude Mythos 5 和 Fable 5 能力接近，但解除部分安全限制，只给受信任项目使用。

这个命名细节重要，因为它决定了两件事。

第一，普通程序员不用等 Mythos 5。能接入的就是 Fable 5。

第二，Fable 5 不是简单替换所有旧模型的默认答案。它价格更高、会跑更长、还有更强的安全分类器。用对地方，收益很大；用在普通小任务上，可能只是把成本和等待时间抬上去。

程序员该关心的不是分数，而是任务粒度

官方基准图很好看。Fable 5 在 SWE-Bench Pro 上是 80.3%，在 FrontierCode Diamond 上是 29.3%，在 Terminal-Bench 2.1 上是 88.0%。

WECHATIMGPH_2

这些数字可以当背景，但不能直接变成工作流。

对程序员更有用的问题是：哪些任务以前 AI 经常烂尾，现在值得重新试？

我会优先看四类。

第一类是代码库级迁移。比如把旧 API 全仓迁到新 SDK，把一套鉴权逻辑拆出去，或者把多处重复配置收敛成统一入口。这类任务难点不在“会不会写代码”，而在能不能读懂上下文、发现边界、逐步修改、跑测试、修回归。

Anthropic 在发布文里提到一个早期案例：Stripe 在 5000 万行 Ruby 代码库里，用 Fable 5 一天完成了一次代码库级迁移，原本需要一个团队手工做两个多月。这个案例不能直接外推到所有公司，但它说明模型能力开始碰到真实工程流程的痛点。

第二类是疑难 bug 排查。特别是那种日志、历史提交、配置、测试、依赖版本混在一起的问题。过去让模型看一个报错，它容易给一个“像答案”的修复；现在更值得让它沿着仓库、测试和运行结果一路追。

第三类是前端和视觉任务。Fable 5 的视觉能力被官方单独强调，示例包括从复杂截图重建 Web App 源码。对前端程序员来说，这比“看图写 CSS”更实用：把设计稿、截图、DOM、现有组件库一起给它，让它先还原页面，再跑截图对比。

第四类是长链路 Agent 任务。比如让 Claude Code 从需求开始，建立分支、读代码、改实现、跑测试、修失败、写交付说明。这里的关键不是模型输出一段好看的解释，而是模型在长时间工具调用中不忘目标。

长上下文不是让你乱塞资料

Fable 5 默认支持 1M token context window，单次请求最多 128k output tokens。这个规格对程序员很诱人，因为终于可以把更多代码、日志、文档、设计资料塞进去。

但长上下文不是免费记忆。

更大的上下文窗口，解决的是“放不下”的问题，不自动解决“读得准”和“改得稳”的问题。你把整个仓库、十几份需求文档、几百行日志一起丢进去，模型仍然需要知道任务边界、优先级、验证标准和停止条件。

我更建议把 1M context 当成“允许更完整地交代现场”，而不是“省掉工程拆解”。

一个更稳的用法是：

  • • 把目标说清楚：要迁什么、保留什么行为、成功标准是什么。
  • • 把边界说清楚：哪些目录不能动、哪些重构不要做、哪些风险必须先问。
  • • 把验证说清楚：跑哪些测试、看哪些截图、用哪些命令证明完成。
  • • 把上下文分层：需求、关键文件、相关日志、历史决策、失败记录分开给。

长上下文的价值，是让模型少在信息缺口里猜；不是让人类放弃组织信息。

Fable 5 更像“资深外包”，不是“自动同事”

Fable 5 prompting 文档里有一个很值得注意的提醒：它适合 hours、days、weeks 级别的问题，简单任务反而不能测出它的能力范围。

这句话放到工程里，可以翻译成一句更朴素的话：不要只拿它写一个函数。

写函数是模型能力的下限。Fable 5 的上限，要在“持续做事”里才看得出来。

比如你可以这样交给它一个需求：

目标：把仓库里的旧版 billing client 迁移到 v3 SDK。

边界：
- 不改公开 API。
- 不引入兼容层，除非测试证明必须。
- 不顺手重构无关模块。

执行：
- 先列出调用点和迁移风险。
- 分批修改，每批后运行相关测试。
- 如果发现行为不一致，先定位原因，再决定是否调整实现。

验证：
- 运行 unit tests 和 billing integration tests。
- 汇总修改文件、失败测试、修复方式和剩余风险。

暂停条件：
- 需要生产密钥、需要删除数据、需要改变公开接口时停止并询问。

这个 prompt 的重点不是写得花，而是把“交付合同”说清楚。

Fable 5 越强，越要给边界。强模型不是只会多做正确的事，也更可能多做你没要求的事。高 effort 下，它可能会多搜索、多分析、多修一点周边问题。对长任务来说，这有时是好事；对一个小 bugfix 来说，这就是风险。

API 接入不是只改 model 字符串

如果你在产品里用 Claude API，迁移到 Fable 5 至少要检查五个地方。

第一，模型名改成 claude-fable-5。

这一步最简单，但也是最容易让人误以为“迁移完成”的地方。

第二，重新设置 effort。

Fable 5 的 adaptive thinking 常开，不能用 thinking: {"type": "disabled"} 关掉。官方建议用 effort 控制智能、延迟和成本。大多数任务从 high 开始；长时间复杂编程任务用 xhigh；简单分类、快速查找、批量子任务可以降到 medium 或 low。

这对工程系统很关键。以前你可能用“换模型”控制质量和成本，现在可以在同一个模型里用 effort 分层。

第三，处理 refusal。

Fable 5 有更强的安全分类器。被拒绝时，Messages API 返回的是成功 HTTP 响应，但 stop_reason 是 refusal。这不是网络错误，也不应该被当成普通模型失败。

如果你的产品涉及安全分析、代码审计、依赖漏洞排查，要特别注意误伤。官方提供 fallbacks 参数和 SDK middleware，可以把被拒绝的请求重试到其他 Claude 模型。拒绝发生在输出前时不计费，但 fallback 模型会按自己的价格计费。

第四，重算 token。

Fable 5 使用 Opus 4.7 引入的新 tokenizer。官方 release notes 提到，相比更早模型，同样文本大约会产生 30% 更多 tokens。长上下文应用、RAG、代码库分析、Agent 工具日志，都应该重新用 token counting API 测一次，不要沿用旧预算。

第五，检查数据保留。

Fable 5 和 Mythos 5 要求 30 天数据保留，不支持 Zero Data Retention。对个人项目这可能不是问题；对企业代码、客户数据、医疗、金融和受监管场景，这不是小字条款，而是上线前必须确认的合规边界。

我会怎么用它

我不会把 Fable 5 设成所有任务默认模型。

日常小任务，例如改一个样式、补一个类型、写一段普通脚本、解释一个报错，优先用更快更便宜的模型。程序员要的是吞吐，不是每次都开最大档。

我会把 Fable 5 留给这些任务：

  • • 跨模块迁移：调用点多、测试多、需要保持行为一致。
  • • 长链路调试：需要读日志、查历史、跑命令、反复验证。
  • • 代码审查：不只看 diff，还要追依赖、边界条件和隐藏回归。
  • • 截图到实现：从设计稿、截图或旧页面还原可运行界面。
  • • Agent 工作流：需要多个子任务、长时间运行、最后汇总证据。
  • • 复杂重构：目标明确、边界明确、可以用测试证明结果。

这里有一个简单判断标准：如果这个任务失败后，你只需要重问一句，那不一定值得上 Fable 5；如果失败后你要花半天收拾烂摊子，才值得用更强模型和更严格的验证流程。

最大坑：把长任务交出去，却不给验收标准

Fable 5 会让更多程序员产生一个错觉：既然模型更强，我就可以少说一点。

实际应该反过来。

模型越能接长任务，人类越应该把验收标准写清楚。因为任务粒度变大以后，错误也会变大。一个函数写错，改一行；一次迁移方向错，可能动几十个文件。

我建议把长任务交给 Fable 5 前，先写一张小清单：

检查项要写清什么
目标最终要交付什么，不要只写“优化一下”
非目标哪些顺手改动不要做
风险区哪些目录、接口、数据不能碰
验证必跑测试、截图、lint、类型检查、手动命令
证据最终报告必须列出运行过的命令和结果
停止条件遇到 destructive、权限、生产数据、公开接口变化时暂停

这张表比“请认真一点”有用得多。

结论：该升级的不是模型名，而是交付方式

Claude Fable 5 的发布，真正值得程序员关注的不是“Claude 5 终于来了”，而是 AI 编程的协作边界又往外推了一段。

以前更适合交出去的是局部代码。现在可以开始试着交出去的是一段工程流程。

但流程交出去，不等于责任交出去。

我的建议很直接：

  • • 小任务继续用便宜快的模型，别浪费 Fable 5。
  • • 长任务用 Fable 5，但必须给目标、边界、测试和暂停条件。
  • • API 产品先补 effort、refusal、fallback、token 预算和数据保留检查。
  • • Claude Code 用户先升级到 2.1.170，再拿真实仓库里的长任务测，不要只测 toy demo。

这次 Claude 5 最适合程序员试的，不是“帮我写代码”，而是“帮我把这件工程任务做到有证据可以验收”。
