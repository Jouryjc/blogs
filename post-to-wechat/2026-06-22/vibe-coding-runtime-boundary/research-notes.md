## Main Spine

The article argues that the dangerous part of vibe-coded internal tools is often not the code generation itself, but the runtime boundary around the generated app.

The example is a support console generated by Claude Code. The app includes an `Issue Credit` action that changes a customer balance. It works locally, but the first version has no authorization, no approval gate, and no audit trail. The author then uses Retool as the runtime layer that supplies identity, permissions, resource-level data access, approvals, and logs.

## External Grounding

- Retool governance docs describe three access layers: organizational access, project access, and data access. They also describe RBAC, permission groups, resource environments, user attributes, query protections, source control, releases, and audit logs.
- Retool permissions quickstart describes RBAC for organization settings and permission groups for objects such as apps, resources, workflows, and agents. Resource permissions can differ by environment.
- Retool audit-log docs say Retool logs user actions such as query runs, including user information, action, and time. Logs can include query details, parameters, IP address, and response time, with retention and export behavior depending on plan and hosting.
- The Retool docs index lists user tasks for approvals in Workflows, but the specific article's claim about the mutating query tripping an approval gate is treated as the source author's demo observation, not a general platform default.
