Claude Context 深度拆解：给 AI 编程助手装上代码搜索引擎

先说结论。

zilliztech/claude-context 解决的不是“模型不够聪明”的问题，而是“模型每次找代码都太费劲”的问题。

我们平时用 Claude Code、Codex、Cursor 这类 AI 编程助手时，经常会遇到一个很真实的场景：

你问它：“用户登录逻辑在哪？”

它开始到处 grep，读文件，继续 grep，再读文件。运气好，几轮后找到；运气不好，token 花了不少，相关文件还漏了。

Claude Context 的思路很直接：

与其每次临时翻代码，不如先把整个代码库做成一个可搜索的索引。模型需要上下文时，不是把仓库一股脑塞进去，而是通过 MCP 工具查出最相关的代码片段，再放进当前对话。

一句话总结：

Claude Context = MCP 工具层 + 代码切块 + Embedding + Milvus/Zilliz 向量库 + BM25 混合检索。

它不是 Claude 的“永久记忆”，也不是一个完整的编程代理。它更像是给编程助手装了一台专门找代码的搜索引擎。

这项目到底是什么

Claude Context 是 Zilliz 开源的一个代码检索项目。当前仓库是一个 monorepo，核心分三块：

  • • @zilliz/claude-context-core：真正的索引和搜索引擎。
  • • @zilliz/claude-context-mcp：把搜索能力包装成 MCP Server，给 Claude Code、Codex CLI、Cursor 等工具调用。
  • • VS Code Extension：在 IDE 里直接做语义代码搜索。

我阅读的是 master 分支当前版本，npm 上 @zilliz/claude-context-core 和 @zilliz/claude-context-mcp 都是 0.1.7。GitHub 页面显示这个仓库已经有约 8k stars。

它的定位很清楚：让 AI 编程助手能通过自然语言查代码。

比如你可以问：

Find functions that handle user authentication

工具返回的不是一堆文件名，而是带路径、行号、语言和代码片段的搜索结果。模型拿到这些片段后，再继续分析、修改或解释。

真正关键的地方在于：

它把“找上下文”从模型的随缘探索，变成了一次工程化检索。

最小可用路径

如果只想跑起来，路径并不复杂，但前提要说清楚。

你需要三样东西：

  • • Node.js：官方 README 写的是 >= 20.0.0 且 < 24.0.0，并明确提示不兼容 Node.js 24。
  • • Embedding 服务：默认是 OpenAI，也支持 VoyageAI、Gemini、Ollama。
  • • 向量数据库：Milvus 或 Zilliz Cloud。

Claude Code 里可以这样加 MCP：

claude mcp add claude-context \
  -e OPENAI_API_KEY=sk-your-openai-api-key \
  -e MILVUS_ADDRESS=your-zilliz-cloud-public-endpoint \
  -e MILVUS_TOKEN=your-zilliz-cloud-api-key \
  -- npx @zilliz/claude-context-mcp@latest

如果你把配置放到全局 ~/.context/.env，MCP 侧可以更干净：

mkdir -p ~/.context

cat > ~/.context/.env << 'EOF'
EMBEDDING_PROVIDER=OpenAI
OPENAI_API_KEY=sk-your-openai-api-key
EMBEDDING_MODEL=text-embedding-3-small
MILVUS_TOKEN=your-zilliz-cloud-api-key
EOF

然后 MCP 配置只需要启动服务：

npx @zilliz/claude-context-mcp@latest

进入项目后，使用方式很像跟一个普通 coding agent 对话：

Index this codebase

等索引开始后，可以查状态：

Check the indexing status

之后就能问自然语言问题：

Find the code that handles auth token refresh

Claude Context 暴露出来的 MCP 工具主要是 4 个：

  • • index_codebase：索引一个代码库。
  • • search_code：用自然语言搜索代码。
  • • get_indexing_status：查看索引状态。
  • • clear_index：清空某个代码库索引。

这里有个很务实的细节：MCP 工具要求传绝对路径。项目内部也是用代码库的绝对路径生成 collection 名称。所以同一个仓库，如果你用软链路径、另一个 clone 路径、挂载路径分别索引，它会被当成不同代码库。

这不是 bug，而是设计取舍。

适合谁用

Claude Context 最适合的不是小玩具项目，而是中大型代码库。

尤其是这几类场景。

第一，接手陌生老项目。

老项目最大的问题不是代码不存在，而是入口太多、命名不统一、历史包袱多。你搜 login，它可能叫 session；你搜 payment，核心逻辑可能藏在 billing 下面。

语义搜索的价值就在这里：它不是只匹配字面词，而是试图找“意思相近”的代码。

第二，让 AI Agent 更少绕路。

很多 coding agent 出错，不是因为改代码能力差，而是第一步定位上下文就错了。它没找到真正的调用链，却开始自信修改。

Claude Context 不能保证每次都找对，但它能减少那种“先盲读 20 个文件”的消耗。

第三，大仓库里的问题定位。

比如你要问：

Where do we validate webhook signatures?

传统 grep 需要你猜关键词：webhook、signature、verify、hmac、secret。

语义检索更像是先理解你的问题，再去找可能相关的实现。

第四，多工具协作。

它不是只给 Claude Code 用。README 里列了 Codex CLI、Gemini CLI、Qwen Code、Cursor、Windsurf、Cline、Roo Code、Claude Desktop 等 MCP 客户端。只要客户端能接 MCP，理论上都能用。

更准确地说：

Claude Context 把“代码搜索能力”做成了一个标准工具，而不是绑死在某一个 IDE 或某一个 Agent 里。

不适合谁用

也要把话说完整。

如果你的项目只有几千行代码，用它可能有点重。直接 rg、IDE 跳转、LSP 基本就够了。

如果你的公司不允许代码发给外部 embedding 服务，也不能用 Zilliz Cloud，那你需要走本地方案：Ollama 做 embedding，本地 Milvus 做向量库。能做，但部署成本会上来。

如果你要做的是非常精确的符号级重构，比如“找出这个 TypeScript interface 的所有实现，并保证类型层面无遗漏”，那它也不应该替代 LSP。

它擅长的是“先找相关上下文”，不是“证明所有引用都找全”。

所以我的判断是：

Claude Context 应该和 grep、ripgrep、LSP、测试一起用，而不是替代它们。

它的工作流：先索引，再搜索

把 Claude Context 想明白，其实只需要抓住两条链路。

第一条链路是索引：

代码文件 -> 过滤规则 -> 代码切块 -> Embedding -> 写入 Milvus/Zilliz

第二条链路是搜索：

自然语言问题 -> Query Embedding -> 混合检索 -> RRF 重排 -> 返回代码片段

中间所有实现细节，基本都围绕这两件事展开。

第一步：哪些文件会被索引

它不是把所有文件都塞进去。

源码里的默认支持扩展包括：

  • • TypeScript / JavaScript：.ts、.tsx、.js、.jsx
  • • Python：.py
  • • Java / C / C++ / C# / Go / Rust
  • • PHP / Ruby / Swift / Kotlin / Scala
  • • Markdown 和 Jupyter Notebook

默认也会忽略常见噪音：

  • • node_modules
  • • dist、build、out
  • • .git
  • • IDE 配置目录
  • • cache、log、temp
  • • .env
  • • minified、bundle、source map 文件

除此之外，它还会合并这些规则：

  • • MCP 调用时传入的 customExtensions
  • • 环境变量 CUSTOM_EXTENSIONS
  • • MCP 调用时传入的 ignorePatterns
  • • 环境变量 CUSTOM_IGNORE_PATTERNS
  • • 项目根目录下的 .gitignore 和各种 .xxxignore
  • • 全局 ~/.context/.contextignore

所以文件选择规则可以简化成一句话：

最终文件 = 支持的扩展名集合 - 忽略规则集合

这点很重要。

如果你是前端项目，想让它索引 .vue、.svelte、.astro，不要指望它自动猜。更务实的做法是显式配置：

CUSTOM_EXTENSIONS=.vue,.svelte,.astro

如果仓库里有大量生成文件，也别让它乱吃。加 .contextignore 比事后抱怨搜索质量更有效。

第二步：代码怎么切块

Claude Context 默认使用 AST splitter。

也就是说，它不是简单按固定字符数切，而是先用 Tree-sitter 解析代码结构，再尽量按函数、类、方法、接口、类型别名这些逻辑单元切。

以 TypeScript 为例，它会关注：

  • • function_declaration
  • • arrow_function
  • • class_declaration
  • • method_definition
  • • interface_declaration
  • • type_alias_declaration
  • • export_statement

这样做的好处很明显。

一个函数最好不要被硬切成两半。一个 class 的关键方法最好能作为相对完整的片段被检索出来。否则模型拿到半段代码，很容易理解错。

但它也没有把 AST 神化。

源码里有 fallback：如果语言不支持 AST，或者解析失败，就退回 LangChain 的字符切分。

默认 chunk 大小是 2500 字符，overlap 是 300 字符。大块代码会继续拆，小块之间会加一点重叠，避免边界处丢上下文。

这就是一个很典型的工程取舍：

能用结构化切分，就尽量保留代码语义；结构化切不动，就退回朴素切分，保证系统继续可用。

第三步：Embedding 怎么做

代码切块之后，每个 chunk 会被送去生成 embedding。

当前支持四类 provider：

  • • OpenAI，默认模型是 text-embedding-3-small
  • • VoyageAI，默认模型是 voyage-code-3
  • • Gemini，默认模型是 gemini-embedding-001
  • • Ollama，默认模型是 nomic-embed-text

这里要注意两个点。

第一，不同 embedding 模型的向量维度不同。

项目会在创建 collection 前检测 embedding dimension，然后用这个维度创建 Milvus schema。比如 OpenAI text-embedding-3-small 是 1536 维，text-embedding-3-large 是 3072 维。

第二，batch size 会影响索引速度。

环境变量里有：

EMBEDDING_BATCH_SIZE=100

默认是 100。你可以根据 provider 的吞吐能力调大，比如 MCP README 里示例给到 512。

但别只想着调大。

batch 太大可能撞 provider 限流，也可能让失败重试更痛。比较稳的做法是先用默认值跑通，再根据索引耗时和错误率调。

第四步：向量库里存什么

Claude Context 用 Milvus 或 Zilliz Cloud 存代码 chunk。

每个 chunk 不是只存向量，还存这些信息：

  • • content：原始代码片段。
  • • relativePath：相对代码库的文件路径。
  • • startLine / endLine：行号范围。
  • • fileExtension：文件扩展名。
  • • metadata：语言、代码库路径等附加信息。

如果开启默认的 hybrid mode，还会多一个 sparse_vector 字段，用 BM25 函数从 content 自动生成稀疏向量。

collection 名称也有设计：

hybrid_code_chunks_<absolute_path_md5_prefix>

它根据代码库的绝对路径做 MD5，再取前 8 位。这样不同项目不会混在一起。

chunk id 则由：

relativePath:startLine:endLine:content

做 sha256 后生成。

这意味着一个 chunk 只要内容或位置变化，id 就会变化。后面做增量更新时，就可以按文件粒度删旧 chunk、插新 chunk。

第五步：搜索为什么不是只做向量

这是我觉得项目里最值得讲清楚的一点。

Claude Context 默认不是单纯 dense vector search，而是 hybrid search。

搜索时它会做两路检索：

  • • Dense vector：把你的自然语言问题转成 embedding，找语义相近的代码。
  • • Sparse vector / BM25：把你的原始 query 当文本，找关键词匹配强的代码。

然后用 RRF，也就是 Reciprocal Rank Fusion，把两路结果融合重排。

说人话就是：

一路负责“意思像不像”，一路负责“关键词对不对”，最后再合并排名。

为什么要这么做？

因为代码搜索很特殊。

如果你问“认证逻辑在哪里”，语义搜索很有用。但如果你搜索 refreshToken、UserSessionManager、__iso_year 这种具体符号，BM25 反而非常重要。

单纯语义搜索可能觉得意思相近就行；但代码里很多时候，精确名字就是关键证据。

混合检索就是在两者之间找平衡。

第六步：索引不是同步卡死的

MCP 里的 index_codebase 会立即返回，真正索引在后台跑。

这点体验上很关键。

大仓库索引可能要很久。如果工具调用一直阻塞，Agent 就会像卡住一样。Claude Context 的设计是：

  • • 先标记当前代码库进入 indexing
  • • 后台扫描文件、切块、embedding、写入数据库
  • • 进度写到本地 snapshot
  • • 用户可以随时查状态
  • • 索引中也可以搜索，但结果可能不完整

状态主要有 4 种：

  • • indexed：已完成，可以搜索。
  • • indexing：后台索引中。
  • • indexfailed：索引失败，可以重试。
  • • not_found：还没索引。

进度百分比不是严格的“文件完成比例”，而是阶段型进度。官方文档也说明了：0% 是准备 collection，约 5% 是扫描文件，10% 到 100% 才是处理文件、生成 embedding、写入向量库。

所以看到它很快跳到 10%，不要误解成已经索引了 10% 文件。

第七步：增量更新怎么做

Claude Context 里还有一个 FileSynchronizer。

它会给文件内容算 hash，并把文件状态保存到：

~/.context/merkle/<codebase_path_hash>.json

内部有一个 Merkle DAG，用来快速判断文件集合有没有变化。

当检测到变化后，它会进一步比较：

  • • added：新增文件
  • • removed：删除文件
  • • modified：修改文件

然后做对应处理：

  • • 删除文件：删掉向量库里这个文件对应的 chunks。
  • • 修改文件：先删旧 chunks，再重新切块、embedding、写入。
  • • 新增文件：直接新增索引。

这个设计的价值在于：

大仓库最怕每次改一点代码都全量重建索引。增量更新能把成本压下来。

但这里也要注意一个边界：

增量更新依赖本地 snapshot 和向量库状态一致。如果你换机器、换路径、手工删 collection，状态就可能不一致。项目里也写了不少 snapshot recovery、0/0 旧状态修复的逻辑，说明作者确实踩过这类坑。

遇到状态异常时，最简单的处理通常是：

clear_index -> 用同一个绝对路径重新 index

它和 grep 到底差在哪

grep 很好，rg 更好。

但 grep 的前提是：你得知道该搜什么词。

如果你知道函数名、变量名、错误码，grep 是最直接的。

但如果你只知道业务含义，比如：

哪里处理了订单过期后的退款？

那你要猜很多关键词：

order expired refund timeout payment cancel

一个都猜不中，就找不到。

Claude Context 的价值在于，把“猜关键词”换成“描述意图”。

不过它也不是 grep 的替代品。

我的建议是：

  • • 找概念、业务逻辑、相似实现：先用 Claude Context。
  • • 找精确符号、错误字符串、配置项：直接用 rg。
  • • 做类型级影响面分析：用 LSP 或编译器。

更务实的组合是：

Claude Context 找方向，rg 和 LSP 做确认，测试做闭环。

官方评测怎么看

仓库里有一个 evaluation 目录。作者做了一个对照实验：

  • • 数据来自 SWE-bench Verified。
  • • 选了 30 个实例。
  • • 过滤成 15 到 60 分钟难度、且正好需要修改 2 个文件的问题。
  • • baseline agent 只有 read、grep、edit。
  • • enhanced agent 在同样基础上增加 Claude Context MCP。
  • • 默认模型用 GPT-4o-mini。
  • • 每种方法独立跑 3 次。

结果是：

指标grep only加 Claude Context MCP变化
平均 F10.400.40基本相当
平均 token73,37344,449下降 39.4%
平均工具调用8.35.3下降 36.3%

这组数据的意思不是“代码能力提升 40%”。

更准确的说法是：

在这组实验里，检索质量基本相当，但 agent 少花了大约 40% token，少调用了三分之一工具。

这很符合 Claude Context 的定位。

它不是让模型突然会写更复杂的代码，而是减少模型为了找到上下文所花的路费。

这里也要看一个细节：评测 README 说结果测试在 claude-context-mcp@0.1.0 上。现在 npm 包已经到 0.1.7。所以这组数据可以作为方向参考，但不要当成所有仓库、所有任务、所有模型上的绝对承诺。

优点：它做对了什么

第一，方向对。

LLM 编程最贵的环节之一，就是找上下文。上下文找错，后面越努力越危险。Claude Context 把这个问题抽成独立工具，方向很清晰。

第二，MCP 形态对。

它没有只做一个 VS Code 插件，也没有只服务 Claude Code，而是把能力暴露成 MCP Server。这样不同客户端都能接入。

第三，混合检索比纯向量更适合代码。

代码既有语义，也有符号。Dense vector 负责语义，BM25 负责关键词，RRF 做融合，这是一个比较务实的方案。

第四，AST 切块是必要的工程细节。

如果把代码按字符硬切，很多函数会被切断。AST splitter 至少让主流语言的 chunk 更接近“代码自然单元”。

第五，支持本地化路径。

如果你在意数据不出门，可以用 Ollama 做 embedding、本地 Milvus 做向量库。它不是默认最简单的路径，但至少架构上留了口子。

第六，有增量索引意识。

大仓库全量重建索引太重。它用文件 hash、Merkle snapshot、按文件删旧写新来降低重复成本。

缺点：不要忽略这些坑

第一，部署比普通工具重。

你不只是装一个 npm 包，还要准备 embedding provider 和向量数据库。对个人项目来说，这个门槛不低。

第二，首次索引有成本。

代码越大，文件越多，embedding 调用越多。你省的是后续检索成本，不是完全免费。

第三，搜索不是证明。

语义检索返回 topK 结果，并不意味着相关代码全部找齐。它适合召回候选上下文，但不能替代静态分析。

第四，路径身份容易踩坑。

同一份代码，用不同绝对路径索引，就是不同 codebase。软链、挂载目录、CI 路径，都可能造成重复索引或状态错乱。

第五，文件支持需要维护。

默认支持很多主流语言，但 .vue、.svelte、.astro 这类文件要自己加扩展。公司内部 DSL、模板文件也一样。

第六，隐私和合规要认真看。

如果你用 OpenAI、VoyageAI、Gemini 做 embedding，代码片段会发给外部服务。很多团队不能接受。这个时候就要评估 Ollama + 本地 Milvus 的方案。

第七，chunk 粒度天然有取舍。

chunk 太小，丢上下文；chunk 太大，召回不准、token 变贵。默认值适合多数场景，但不是所有仓库的最佳值。

和其他工具的关系

可以这样理解。

grep / rg 是字符串搜索。

LSP 是符号和类型理解。

Context7 更偏“最新文档和示例”，解决的是库文档幻觉问题。

DeepWiki 更偏“把仓库生成可读文档”。

Serena 这类工具更像“完整的 coding agent 工具箱”，会结合语言服务器和符号级能力。

Claude Context 的重点更窄：

它专注把你的代码库做成一个 AI Agent 可调用的语义搜索索引。

这也是它的优势和边界。

优势是专注，边界也是专注。

我会怎么落地使用

如果让我在团队里试用，我不会一上来全员推广。

我会按这个顺序来。

第一步，选一个中大型、但不涉及最高敏感级别代码的仓库。

先验证：

  • • 初次索引耗时多久。
  • • 平均搜索延迟多少。
  • • top10 结果是否真的能帮 agent 少读文件。
  • • embedding 和 Zilliz/Milvus 成本能不能接受。

第二步，先配置 .contextignore。

别把生成文件、快照、fixtures、大型 JSON、测试金数据都塞进去。索引垃圾越多，检索结果越容易被污染。

第三步，为项目补扩展名。

前端项目常见：

CUSTOM_EXTENSIONS=.vue,.svelte,.astro

后端项目可能还有：

CUSTOM_EXTENSIONS=.sql,.graphql,.proto

但不要贪多。只加你真的希望 agent 读的文件。

第四步，给 agent 固定一套提问方式。

比如：

先用 claude-context 搜索和“刷新 token”相关的代码，
返回最相关的 10 个结果。
然后再用 rg 验证精确符号。

这样比直接说“帮我修一下登录问题”稳定很多。

第五步，把它当作定位工具，不要当最终裁判。

代码修改前后还是要跑测试。涉及类型、引用、迁移、权限、安全逻辑时，更要用编译器、LSP、单测和人工 review 收口。

如果只用一句话评价

Claude Context 的价值，不是“让上下文窗口更大”，而是“让进入上下文的代码更准”。

大上下文窗口当然有用。

但大上下文有两个问题：

  • • 贵。
  • • 容易把无关内容也带进去。

Claude Context 走的是另一条路：

先把仓库离线索引起来，问题来了再按需取相关片段。

这更像传统搜索引擎和 RAG 的思路，只是对象从文档变成了代码，调用者从人变成了 AI Agent。

我比较看好这个方向。

未来的 AI 编程助手，不应该每次都像第一次见到你的代码库。它应该有一套可复用的检索层，能快速知道“相关代码在哪里”。

Claude Context 还不是终点。

它还需要更好的符号理解、更细的语言生态支持、更稳定的本地化部署体验，以及和测试、LSP、代码审查工具更紧的组合。

但它已经把一个关键问题讲清楚了：

Agent 写代码之前，先要会找代码。

这件事做好了，后面很多能力才有意义。
