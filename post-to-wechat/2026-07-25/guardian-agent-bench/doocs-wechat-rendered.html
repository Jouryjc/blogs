给 Agent 加一句“谨慎调用工具”，不等于它真的会谨慎。

一篇刚发布的论文测了 580 个工具场景：哪怕是表现最好的模型和框架组合，整体正确率也只有 74.8%。更意外的是，强模型最常见的失败不是“乱点按钮”，而是该调用的工具没调用。

这对正在做 Agent 的团队很实际：如果系统已经能发邮件、改日程、查财务数据，安全不能只写在 system prompt 里。每次工具调用执行前，都应该有一道能检查、纠错和阻断的闸。

这次测试，不只看 Agent 最后说对没有

这篇论文叫《GuardianAgentBench: Where Agents Fail and How to Guard Them》。

研究团队构造了 580 个场景，覆盖客服、邮件、日历、商业智能、金融和内部知识库六个领域，一共涉及 81 个工具、1,177 个顺序步骤。

每个场景不只检查最终回答，还检查完整动作轨迹：

  • • 该调用哪些工具；
  • • 参数传得对不对；
  • • 必要步骤有没有漏；
  • • 工具之间的依赖顺序是否正确；
  • • Agent 有没有重复调用同一个错误工具。

其中 182 个场景还被故意“下了绊子”：工具返回超长数据、认证错误、多个模糊匹配、Prompt Injection，或者只返回一半数据。

这比只测问答准确率更接近生产环境。Agent 的回答可以听起来很完整，但只要漏查一次冲突、拿错一个客户 ID，后面的动作仍然可能全部失效。

最强组合，也会在四个任务里错一个

论文测试了六个模型，并把它们分别放进 LlamaIndex、LangChain 和 Vectara。

最佳组合是 Claude Opus 4.5 加 Vectara，平均 Overall 只有 74.8。日历任务尤其难，没有一个模型超过 62.0。

这组数字不能直接等同于所有生产 Agent 的成功率。论文要求每个场景只有一条明确的标准路径，现实任务通常允许多种合理做法。

但它足以说明一个问题：模型能力很强，不代表工具链已经可靠。

同一个模型换三个框架，分数通常只差 2～3 分。至少在这组测试里，从 LangChain 换成 LlamaIndex，不会自动把工具失败消掉。问题更多出在模型如何维持任务计划，而不是框架名字。

强模型怕漏，弱模型怕乱

论文把错误分成五类：选错工具、参数错误、漏掉必要调用、重复调用、调用顺序错误。

结果出现了两种很不同的失败画像。

强模型更容易“少做一步”。GPT-5.2 Pro 的失败里，漏掉必要工具调用占 56.7%～57.2%；Gemini-3-Pro 也在 52.1%～54.7%。

较弱模型更容易“做错很多步”。DeepSeek-V3.2 和 Qwen3-Max 的选错工具、重复调用比例更高。

两种失败画像，需要两套不同的拦截重点：

失败画像常见表现更合适的防护
少调用忘记查冲突、漏掉资格校验Tool Coverage：检查必要步骤
乱调用选错工具、重复重试Relevance / Cost：拦截无关与重复调用
参数错ID 缺失、格式不合 schemaArgument Validation：参数与上下文校验

模型越强，越不能只盯着“有没有乱调用”。它可能回答得很稳，却悄悄省掉一项关键检查。

WECHATIMGPH_1

工具变多会掉分，任务链变长掉得更快

研究团队还测了工具数量和任务深度。

Claude Opus 4.5 面对 1 个工具时，平均分是 78.2；工具增加到 7 个，降到 62.3。

如果把任务从 1 层依赖拉到 7 层，分数则从 82.3 降到 51.2。长链任务带来的降幅，差不多是工具数量增长的两倍。

这里有个容易误读的地方。论文同时发现，“工具顺序错误”只占全部失败的 0.6%～4.4%。

顺序错得少，不等于长任务已经解决。Agent 可能没有把 A、B 调反，却会在跑到第五步时漏掉 C，或者因为前一步返回不完整数据而提前收工。

生产系统要防的不是单纯的排序错误，而是整条计划在多轮执行中逐渐缺步骤。

WECHATIMGPH_2

多写一段安全提示，为什么不够

论文比较了两种防护：

第一种是在 system prompt 里加入更明确的安全和工具使用说明。

第二种是在工具执行前插入 guardrail，读取当前计划、上下文、候选工具和参数，再决定放行、纠错或阻断。

对强模型，安全提示几乎没有帮助：

  • • Gemini-3-Pro：+0.3；
  • • Claude Opus 4.5：+0.4；
  • • GPT-5.2 Pro：-0.3。

而执行时 guardrail 在六个模型上都带来了提升，范围是 +2.8 到 +7.7。

在 Claude Opus 4.5 + LlamaIndex 的 580 个场景中，guardrail 修复了 151 个原失败场景里的 30 个，恢复率 19.9%；429 个原本成功的场景里，只误伤了 2 个，误报率 0.5%。

区别不难理解。Prompt 是建议，执行层是约束。

如果 Agent 准备调用 send_email，执行层可以在邮件真的发出去前检查：收件人是否来自可信上下文、附件是否齐全、前置审批是否完成、这个动作是否需要人确认。

WECHATIMGPH_3

把论文结论落到工程里：四层工具闸门

如果我现在要上线一个能产生副作用的 Agent，会把每次工具调用拆成四层检查。

第一层：参数是否合法

先做确定性校验：schema、类型、必填字段、枚举值、ID 格式、数值范围。

能用代码判断的，不交给另一个模型猜。

第二层：步骤是否完整

根据任务类型维护必要动作清单。

例如创建会议前必须查冲突，退款前必须查订单与退款资格，发邮件前必须确认收件人与附件。Agent 漏掉前置动作时，不直接执行，而是返回结构化反馈让它补计划。

第三层：动作是否值得执行

检查重复调用、无关调用、调用次数和预算。一个搜索工具连续拿到相同错误时，不允许 Agent 无限制重试。

LangChain 官方已经提供 tool-call limit、middleware 和 wrap_tool_call 这类入口，可以把限制放在 Agent 循环周围，不需要重写整个框架。

第四层：副作用是否需要人批

读数据和发邮件不是一个风险等级。

删除生产数据、转账、对外发送消息、修改权限，应该进入 Human-in-the-Loop。审批界面至少要给人看清：Agent 想做什么、参数是什么、依据来自哪里、不批准会怎样。

可以直接把下面这张清单放进上线评审：

  • • [ ] 每个工具都有严格 schema 和参数边界
  • • [ ] 高风险动作有 allow / deny / review 规则
  • • [ ] 关键任务定义了必要工具覆盖检查
  • • [ ] 重复调用、总调用次数和成本有上限
  • • [ ] 工具返回错误、部分数据和多匹配时不会静默继续
  • • [ ] Prompt Injection 内容不会直接变成工具指令
  • • [ ] 阻断后给 Agent 结构化纠错信息
  • • [ ] 多次纠错失败会升级给人
  • • [ ] 日志能还原计划、调用、参数、结果与 guardrail 判定

这篇论文也有三条边界

第一，guardrail 只集成在 LlamaIndex 上做了实验，不能据此断言所有框架接入后都有同样收益。

第二，三个 guardrail 由 Claude Sonnet 4.5 驱动，并非全部是便宜的静态规则。论文没有给出完整延迟和成本数据。生产实现应该把 schema、权限、次数限制留给确定性代码，只把语义判断交给模型。

第三，Benchmark 排除了“多条路径都合理”的场景，以便得到唯一标准答案。这提升了评测稳定性，也让它和开放世界任务之间留了一段距离。

所以，74.8 不是行业通用成功率，19.9% 也不是接入 guardrail 后必然得到的收益。可复用的结论是防护位置：工具调用执行前。

最后

过去我们习惯把 Agent 安全写成一段更长的 system prompt。

GuardianAgentBench 给出的工程提醒更具体：模型负责提出动作，系统负责决定动作能不能发生。

如果你的 Agent 已经能发邮件、改数据库、调支付接口，先别继续堆安全提示。把上面的“四层工具闸门”收藏下来，逐项检查参数、覆盖、成本和人工审批。
