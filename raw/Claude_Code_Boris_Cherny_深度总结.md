# 深度总结：Claude Code 负责人 Boris Cherny — 编程被"解决"之后会发生什么？

## 一、嘉宾背景

Boris Cherny 出生于乌克兰敖德萨（Odessa），1995 年举家移民美国。他是 Claude Code 的创始人和负责人，也是《Programming TypeScript》一书的作者。在这期播客中，他回顾了 Claude Code 从一个终端原型成长为改变整个软件工程行业的工具的历程，同时分享了对 AI 未来、团队文化、安全性以及职业角色演变的深刻见解。

值得一提的是，Boris 曾短暂离开 Anthropic 加入 Cursor，但仅两周后便回归。驱使他回来的核心原因是 Anthropic 的使命——确保 AI 安全地造福人类——这让他感到自己的工作更有意义。

---

## 二、Claude Code 的爆发式增长

### 2.1 关键数据

- Claude Code 已贡献了 **GitHub 公开代码提交量的约 4%**，根据 Semi Analysis 的报告，预计到年底可能达到约 **20%**（私有代码库的比例可能更高）。
- Claude Code 的日活跃用户在过去一个月内**翻倍**，增长仍在加速。
- Boris 本人自 2025 年 11 月以来，**100% 的代码都由 Claude Code 编写**，他没有手动编辑过一行代码，每天通过约 5 个 agent 并行处理，能发出 10–34 个 Pull Request。
- 每位工程师的生产力提升了约 **200%**。
- Spotify 的顶级开发者自 2025 年 12 月以来同样没有手写过一行代码。

### 2.2 产品形态扩展

Claude Code 已从最初的终端工具发展为一个多平台产品矩阵：iOS/Android 应用、桌面端应用、IDE 插件（VS Code/JetBrains）、Slack 集成、GitHub 集成等。CoWork（后文详述）进一步将能力延伸到非编码领域。

## 三、Claude Code 的诞生故事

### 3.1 从一个 Hack 开始

Claude Code 最初是 Anthropic 内部的一个实验项目——一个关于"如果模型不仅能说话还能行动，编程会变成什么"的探索。当时只有 Boris 一个人参与，终端界面是最简单的选择，所以第一版就是一个终端工具。

早期 Demo 视频展示了一个令人意外的能力：系统用 bash 工具回答了"我现在在听什么音乐"这样的问题——这是团队都没有完全预想到的用途。然而，当 Boris 把 Demo 发到内部时，只收到了**两个赞**。这恰恰证明了一个规律：**真正的创新在变得不可或缺之前，常常看起来很无聊。**

### 3.2 "潜在需求"（Latent Demand）原则

Claude Code 的发展轨迹很好地诠释了"潜在需求"这一产品原则。Boris 将其定义为：**用户用产品做了它并非为之设计的事情——这就告诉你下一步该往哪走。**

早期用户主要用 Claude Code 写代码，但很快他们开始用它做非编码任务：缴停车罚单、管理项目、跨电子表格和 Slack 自动化日常事务、甚至进行基因组分析工作。这些"野生用法"指引了产品的下一步方向。

## 四、反直觉的产品原则

### 4.1 不要限制模型

Boris 强调的核心理念是**不要把模型装进盒子里**。与其设计严格的工作流程来约束模型的每一步行为，不如给模型一个工具箱和一个目标，然后让它自己决定如何完成。

传统思维是"围绕系统的某个组件来设计产品"，但 Boris 的方法是"**围绕模型来设计产品**"。不要过度策划，不要限制模型的行动顺序，让模型有即兴发挥的空间。

### 4.2 押注更通用的模型

Boris 引用了 Rich Sutton 的"苦涩的教训"（The Bitter Lesson）：**更广泛、更通用的方法往往在长期内胜过狭窄的、精心调优的方案。** 在一个最新模型可以在一夜之间改变能力格局的领域，灵活的、能随更强模型一起升级的方法，总是优于为特定模型定制的脆弱脚手架。

### 4.3 为未来的模型而构建

Boris 建议不要只为今天的模型构建产品，而是**为 6 个月后的模型构建**。如果你的产品只能在当前模型能力下工作，那当新模型发布时，你可能已经落后了。设计产品时要预留空间来利用未来模型更强的能力。

### 4.4 尽早发布

尽早将产品交到真实用户手中，你才能从真实世界的反馈中发现潜在需求。安全和产品改进都受益于早期的真实使用场景。

## 五、工程文化与团队管理

### 5.1 "资源不足"（Underfunding）策略

Boris 提出了一个看似矛盾的策略：**小团队 + 有限资源，但给工程师无限 token。** 这不是饿死团队，而是通过小团队逼出效率和快速迭代。同时，鼓励工程师大量消耗 token 来实验，在真正验证了一个想法之后才去优化成本。Boris 的经验法则是：先给工程师尽可能多的 token 去探索，确认想法可行后再考虑节约。

### 5.2 全员编码

在 Claude Code 团队，每个人都写代码——产品经理编码、工程管理者编码、设计师编码、财务人员编码、数据科学家编码。这些角色之间大约有 50% 的重叠。Boris 预言，到年底"软件工程师"这个头衔可能开始消失，被"Builder（构建者）"所取代。或者说，每个人都是产品经理，同时每个人都写代码。

### 5.3 三条团队原则

Boris 与每位新成员分享三条原则（具体名称在播客中有详述）：
1. 围绕模型而非组件来设计产品
2. 押注通用模型，避免过度定制
3. 为未来的模型能力而构建

## 六、"编程已被解决" —— 印刷术类比

### 6.1 编程作为一个已解决的问题

Boris 做出了一个大胆的论断：**编程在很大程度上已经被解决了。** 至少对于他所做的那类编程而言，Claude 已经可以胜任。现在他们思考的是"下一步是什么"——Claude 开始自主生成想法，查看用户反馈、分析 bug 报告、检查遥测数据，然后提出修复建议和新功能创意，越来越像一个同事而非工具。

### 6.2 印刷术的类比

Boris 用古登堡印刷术来类比当前的变革。印刷术不仅仅是传播了识字能力；它重塑了整个社会的协调和创造能力。他设想一个**每个人都能编程**的未来——软件开发不再被少数专家垄断，而成为一项普遍技能。从汇编语言到 C 到 Python，每一代编程语言都降低了门槛、扩大了程序员群体。AI 是这条曲线上的下一个跳跃点。

### 6.3 杰文斯悖论

Boris 引用了杰文斯效应来解释为什么更强的能力不一定意味着更少的工作：当一种能力变得更便宜、更容易获得时，对它的需求反而会增加。AI 让编程更容易了，但社会对软件的需求也在爆炸式增长——长期来看，这意味着更广泛的转型，而非简单的裁员。

---

## 七、AI 将变革哪些角色

### 7.1 从编码到更广泛的知识工作

Claude Code 已经超越了单纯的代码编写，正在自动化非编码任务：项目管理、内部沟通、缴费、数据分析等。下一步，产品管理、设计和数据科学都将面临转型。AI agent 可以使用工具、自主行动，模糊了传统角色的边界。

### 7.2 Lenny 的调查数据

Lenny 在社交媒体上发起投票，询问工程师、PM 和设计师采用 AI 后是否更享受工作：
- **工程师和 PM**：约 70% 表示更享受
- **设计师**：只有 55% 表示更享受，18% 表示更不享受（几乎是工程师的两倍）

Boris 的回应是 Anthropic 的设计师同样在编码，因此能自行解除阻碍而感到满意。但评论者 Roger Wong 指出，这是"工程师对设计问题的回答"——"能自己解除阻碍"不等于"AI 能做设计"。设计涉及视觉思维、空间推理、用户体验等，这些方面 Boris 并未触及。

### 7.3 角色融合

Boris 预测传统的工程、设计、产品三大领域不会消失，而是会**融合**。角色之间的界限越来越模糊，每个人都需要成为跨学科的通才——同时理解用户、业务、设计和技术基础设施。

---

## 八、在 AI 时代如何成功

Boris 提出了几个关键建议：

1. **拥抱实验**：不断尝试新工具和新方法，不要害怕失败
2. **成为通才**：跨学科思维比深度专精更有价值——理解用户、业务、设计、技术各个维度
3. **跨领域思考**：从多角度审视问题，而非只从自己的专业出发
4. **让模型引导你**：不要试图完全控制 AI，而是学会与它协作，让它去做它最擅长的事

## 九、CoWork 的诞生：10 天的冲刺

### 9.1 从潜在需求到产品

CoWork 是 Claude Code 团队发现用户在将 Claude Code 用于非编码任务后，顺势而为的产物。这款产品在短短 **10 天内**被构建出来——而且完全使用 Claude Code 来开发。

### 9.2 产品定位

CoWork 是一个伴侣产品，将 Claude Code 的能力扩展到代码编写之外。它可以帮助团队自动化治理、项目管理，甚至处理清理桌面、填写表单、跨浏览器执行操作等日常琐事。Chrome 集成是其亮点功能——agent 可以在你的浏览器中行动，登录、填表、整理数字生活。

### 9.3 安全沙箱

CoWork 内置了安全沙箱，将安全性作为功能特性而非事后补救。这个沙箱也被开源，供外部研究者研究和测试。

---

## 十、AI 安全的三层架构

Boris 详细阐述了 Anthropic 的三层安全方法：

### 第一层：对齐（Alignment）
在模型核心层面进行对齐训练，确保模型的行为与人类意图一致。

### 第二层：受控评估（Evals）
在受控环境中进行严格的评估测试，发现潜在的安全问题。

### 第三层：真实世界监控
在实际使用中持续监控和观察模型行为。

### 机制可解释性（Mechanistic Interpretability）
Boris 特别介绍了机制可解释性——一种"窥探模型大脑"的方法。他们可以将神经元映射到具体概念，追踪规划行为是如何从激活网络中涌现的。例如，他们可以监控与"欺骗"相关的神经元，知道它何时被激活。Anthropic 公开发表了大量这方面的研究，甚至开源了部分沙箱工具。

---

## 十一、Agent 时代的焦虑与并行工作

Boris 坦诚地谈到了一个有趣的心理现象：当 agent 没有在运行时，他会感到一种焦虑。他总是保持多个 agent 同时运行，每天早上第一件事就是检查 iOS 上的 Claude Code 应用，看看有什么需要处理。

他的实践建议是**并行运行多个任务**，这样没有任何一个单独的任务会成为瓶颈。同时，他发现"计划模式"（Plan Mode）和使用最新最强的模型（如 Opus 4.6）可以减少 token 浪费，提高效率。

---

## 十二、使用 Claude Code 的实用建议

1. **使用计划模式（Plan Mode）**：让模型先制定计划再执行，减少无效的 token 消耗
2. **使用最新模型**：最新的模型（如 Opus 4.6）往往能更高效地完成任务
3. **向 Claude Code 求助自身优化**：Claude Code 了解自己的设置，可以帮你优化配置
4. **选择最适合的界面**：根据团队和任务选择终端、桌面、移动端或 Slack
5. **并行运行多个 agent**：最大化利用等待时间
6. **利用工具连接**：CoWork 和 Claude Code 支持连接各种外部工具，发挥最大效用

## 十三、关于竞争（Codex 等）

当被问及对 OpenAI Codex 等竞争产品的看法时，Boris 表现得很从容。他的态度是**专注于用户问题**，而非盯着竞争对手。在这个快速变化的领域，真正重要的是持续与用户对话、持续改进产品，而非追踪竞争态势。

## 十四、味噌的故事：长线思维

Boris 分享了他在日本农村的经历——交换腌菜、耐心制作味噌。白味噌需要三个月，红味噌需要两到四年。这个故事看似闲笔，实则意味深长：它代表了一种**长周期思维**的哲学——与 Claude Code 快速迭代的节奏形成了有趣的对照。

Boris 热爱在长时间尺度上思考的能力。这种耐心让当前 AI 带来的变革感觉既不可避免又充满人性温度。如果 AGI 实现了，他的计划之一就是继续做味噌。

## 十六、核心观点总结

1. **编程在很大程度上已被解决**。下一个前沿是让 AI 超越代码编写，走向创意生成、项目管理和跨领域自动化。

2. **我们只完成了 1%**。尽管进展惊人，Boris 认为 AI 辅助革命才刚刚开始，还有巨大的发展空间。

3. **"软件工程师"头衔可能会消失**，取而代之的是"Builder"。每个人都编码，每个人都是某种程度上的产品经理。

4. **潜在需求是产品创新的指南针**。观察用户如何"误用"你的产品，就能找到下一步方向。

5. **不要限制模型**。给模型工具和目标，让它自己选择路径。押注通用模型，为未来而构建。

6. **安全不是事后考虑**。Anthropic 通过三层架构（对齐、受控评估、真实世界监控）和机制可解释性来确保 AI 的安全部署。

7. **AI 编程的民主化类似于印刷术革命**——它将重塑社会的创造和协调能力。

8. **小团队 + 无限 token + 快速迭代** = Anthropic 构建 AI 产品的方法论。
