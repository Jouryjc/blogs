# 把 Claude Code 拆开之后，我更确定：AI Agent 的壁垒在运行时，不在提示词

先说结论。

如果你把 Claude Code 看成“一个会写代码的大模型，再加几把工具”，那你会低估今天 AI Agent 最难做的部分。

这篇在 **2026 年 4 月 14 日** 提交到 arXiv 的论文《Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems》，最有价值的地方，不是告诉你 Claude Code 有多神秘，而是把一个事实讲透了：

**生产级 coding agent 的核心，不是中间那段 agent loop，而是围绕它的一整层运行时。**

先把边界说清楚。

这篇论文**不是 Anthropic 官方白皮书**。它是作者基于公开的 TypeScript 源码、官方文档和一个对照系统做的架构分析。

所以它更像一次“源码考古 + 架构归纳”，不是官方承诺文档。

但也正因为这样，它反而很适合我们回答一个更实在的问题：

**一个能进生产环境的 AI Agent，到底要补哪些基础设施？**

## 这篇论文到底做了什么

作者先不是上来就讲实现细节，而是先提了 5 个价值观：

- 人类决策权
- 安全、隐私与安全边界
- 可靠执行
- 能力放大
- 情境适应

然后再把这些价值观，往下落成 13 条设计原则。

你不用把 13 条全背下来，抓住下面几条就够了：

- 默认拒绝，不认识的动作先拦住，再决定要不要升级给人
- 权限不是二元开关，而是一条渐进信任的谱系
- 安全不是靠单点，而是靠分层防御
- 上下文是稀缺资源，要渐进式管理
- 扩展机制不能只图统一，还要考虑上下文成本
- 子代理要隔离，不能把父代理的上下文和权限原样复制过去
- 会话状态要追加式持久化，方便恢复、回放和审计

如果只用一句话总结这篇论文的方法，那就是：

**它不是在回答“Claude Code 为什么强”，而是在回答“生产级 agent 必须把哪些工程问题做厚”。**

## 如果只记一串数字，记这一串就够了

论文里最有画面感的一组信息，其实是一串数字：

- `1` 个核心循环：调模型、调工具、再调模型，重复直到任务结束
- `7` 个权限模式，加上一层自动分类
- `5` 层上下文压缩/投影机制
- `4` 种扩展机制：`MCP`、`Plugins`、`Skills`、`Hooks`
- 最多 `6` 类内建子代理
- 最多 `54` 个内建工具，其中 `19` 个常驻，`35` 个按条件开启
- 作者估算只有大约 `1.6%` 属于“决策逻辑”，其余 `98.4%` 都在外围运行时基础设施里

这组数字最值得细想的，不是“Claude Code 做得好复杂”。

而是：

**今天一个真正能落地的 agent，复杂度已经明显从 prompt 和 planner，转移到了 runtime 和 harness。**

## 真正关键的地方，不是 loop，而是 loop 外面那一圈

很多人第一次接触 agent，会把注意力放在“模型怎么想”“planner 怎么写”“prompt 怎么设计”上。

这些当然重要。

但这篇论文最想强调的是：

**中间那段 loop 其实很简单，真正复杂的是 loop 外面那一圈工程系统。**

### 1. 权限系统，决定它敢做什么

Claude Code 的核心思路不是“模型想做什么就做什么”。

它更像是：

**模型可以提议动作，但系统要先判断这个动作值不值得信。**

这里面最关键的不是某条 deny rule，而是整体策略：

- 默认先拒绝陌生或高风险动作
- 可逆、只读、低风险的动作放得更开
- 真有风险时，把决定权交还给用户

这背后其实是在解决一个老问题：

**Agent 想要能力，就必须拿到更多权限；但 Agent 拿到更多权限，风险又会急剧上升。**

所以它不是“开”或“关”的问题，而是：

**怎么让权限的开放速度，跟风险的可控速度匹配。**

### 2. 上下文系统，决定它会不会越做越糊

这篇论文还有一个很重要的判断：

**对 agent 来说，真正的硬约束不是算力，而是上下文。**

Claude Code 的做法不是只靠一次摘要，而是把上下文管理做成一个五层渐进系统：

- 先限制单次工具结果的体积
- 再裁旧历史
- 再做更细粒度的压缩
- 再做读时投影
- 最后才做完整的自动 compact

这意味着什么？

意味着系统不是简单地“删上下文”，而是在想办法把上下文从“堆满窗口”变成“按需要重组”。

这件事对 Agent 特别重要。

因为一个能跑几分钟的 demo，和一个能连续跑半小时、一小时的生产系统，中间最大的差别，往往不是模型智商，而是：

**你有没有一套不会让上下文越跑越糊的机制。**

### 3. 扩展系统，决定它能不能从工具变成平台

论文把 Claude Code 的扩展面拆成了 4 种：

- `MCP`：接更多工具和资源
- `Plugins`：做能力打包和分发
- `Skills`：给模型补低成本、可复用的工作方式
- `Hooks`：在关键生命周期挂可编程策略

这层设计特别值得抄。

因为很多团队一开始都想做“一个统一的扩展接口”，听起来很优雅。

但现实通常是：

**不同扩展，消耗的上下文、稳定性、权限和运行时成本，根本不是一个量级。**

所以更务实的做法，不是强行统一，而是按成本分层。

这也是为什么论文会特别强调：

**扩展机制不是越少越好，而是要按使用代价和作用边界拆开。**

### 4. 子代理和持久化，决定它能不能做长任务

很多 agent demo 一到多步骤任务就开始发虚。

原因不复杂：

- 分工一多，上下文互相污染
- 会话一长，状态难恢复
- 中途出错，不知道该从哪里接着跑

Claude Code 在这两块给出的答案很明确：

- 子代理要隔离，最好连工作目录都隔离
- 会话要用追加式日志保存下来

论文里提到，Claude Code 的会话持久化主要是 **append-only JSONL**。

这看起来甚至有点“土”。

但它有两个非常实在的好处：

- 好审计，出了问题能回放
- 好恢复，context 窗口满了也不等于会话生命周期结束

这其实是在提醒我们：

**Agent 的记忆，不只是为了让模型记住事，更是为了让系统出了问题以后还能继续干活。**

## 这篇论文最聪明的地方，是它把 Agent 变成了一张设计问卷

论文后面拿 Claude Code 和 OpenClaw 做了对照，这个部分我觉得特别有启发。

因为它说明了一件事：

**Agent 架构没有唯一标准答案，但每个系统都必须回答同一组问题。**

比如：

- 安全是放在每次动作前后判，还是放在外围边界判
- 扩展是补单个 agent 的能力，还是扩整个网关的平台能力
- 记忆是重点做压缩，还是重点做长期结构化存储
- 多 agent 是做父子式委派，还是做多个独立 agent 路由

Claude Code 的答案，更像是一个 **CLI 场景下、以单任务执行为中心的运行时**。

OpenClaw 的答案，则更像是一个 **多通道、多身份、多 agent 的网关控制平面**。

这也意味着：

**同样的问题，部署上下文一变，最优架构就会跟着变。**

这比“谁更先进”更重要。

因为它告诉我们，设计 agent 时最该先问的不是“我能不能也做个 Claude Code”，而是：

**我这个 agent，到底是给谁用、在哪跑、信任边界在哪里、会话要活多久。**

## 论文没有回避的 3 个难题，才是下一阶段真正要打的仗

我很喜欢这篇论文的一点，是它没有假装自己已经把问题都解决了。

相反，它在最后专门把未来设计问题摊开讲。

我觉得最值得关注的有 3 个。

### 1. 静默失败

最危险的失败，往往不是报错，而是“看起来在正常推进，其实方向已经偏了”。

这类问题只靠更强的模型不一定能解决。

很多时候，需要的是额外的评估层、观测层和 post-check 机制。

### 2. 长时程任务

单会话能跑通，不代表跨天、跨周、跨多轮协作也能跑通。

当任务从一个 session 变成一个长期项目时，光靠当前的上下文压缩和会话恢复，未必够用。

### 3. 人类能力怎么保住

这是我觉得最值得反复想的一点。

论文最后把问题收束到一个很尖锐的方向：

**未来的 agent，不该只优化“替你做更多事”，还要想办法避免把人的理解力、代码一致性和长期判断力一起外包掉。**

这不是哲学问题。

这是工程问题。

因为一个短期看起来很高效、长期却让团队越来越不理解系统的 agent，最后通常会把技术债、协作成本和维护风险一起推高。

## 我的收获

如果你正在做 AI Agent，我觉得这篇论文最值得抄的，不是某个实现细节，而是它的提问方式。

你可以直接拿这 5 个问题，回头审视自己的系统：

1. 你的权限边界，到底是怎么划的？
2. 你的上下文，是怎么一点点丢掉关键信息的？
3. 你的扩展机制，会不会把上下文和安全成本越堆越高？
4. 你的子代理，到底有没有真正隔离？
5. 你的状态一旦出问题，能不能恢复、回放、审计？

把这些问题答清楚，才算开始做“生产级 agent”。

不然很多时候，我们做的还只是一个能跑 demo 的 loop。
