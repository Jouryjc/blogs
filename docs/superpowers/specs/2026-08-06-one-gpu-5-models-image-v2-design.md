为《5 个模型，1 张 GPU：小模型省的钱，别还给 serving》重构 1 张封面图和 5 张正文配图。新图不再沿用旧图的写实服务器、英文信息图或仿 README 截图，而是统一到「蒸馏小余」已经使用的技术手绘风格：奶油纸张底色、深海军蓝线稿、低饱和色块、少量机器人角色，以及一眼能读懂的工程关系。

## 统一视觉系统

### 画面与材质

- 封面使用 2.35:1 横图，建议输出 1920 × 820 或等比例尺寸；关键标题和主体必须位于中央安全区，正方形裁切后仍能识别主题。
- 正文配图使用 16:9 横图，建议输出 1600 × 900 或更高等比例尺寸。
- 背景为带轻微颗粒和纸纤维感的奶油色纸张，不使用纯白背景。
- 图形采用略有手绘抖动的深蓝线条，保留人画出来的松弛感，但文字、箭头和连接关系必须清楚。
- 允许使用小余机器人作为观察者、讲解者或动作引导，不让角色压过技术信息。

### 色彩

- 奶油纸底：`#F6F0E3`
- 主线稿深蓝：`#0B2554`
- 品牌蓝：`#0F4C81`
- 浅蓝卡片：`#DCEBFA`
- 浅绿卡片：`#E2F0DF`
- 浅黄卡片：`#F8E7A8`
- 浅粉卡片：`#F7DAD5`
- 警示红：`#C95B52`

整体保持低饱和度；警示红只用于浪费、冲突、叉号和关键风险，不大面积铺色。

### 中文与信息密度

- 标题使用清楚、有手写感的简体中文，正文标签使用易读的黑体感字形。
- 每张图只保留一个结论，不塞长段解释。
- 技术缩写如 `GPU`、`API`、`LRU`、`PoC` 可保留英文，其余信息尽量中文化。
- 每张正文图底部保留一条短结论条，形成整组图片的共同节奏。
- 生成时必须逐字核对中文；任何乱码、错字、缺字或多余英文都视为不合格。

### 禁止项

- 不使用照片级服务器、真实机房、3D 渲染或赛博霓虹风。
- 不使用玻璃拟态、发光渐变、金属质感和商业图库式人物。
- 不伪造 GitHub、README、终端或监控后台截图。
- 不在一张图里堆叠超过五个同级信息块。

## 六张图片设计

### 1. 封面：五个模型共享一张 GPU

文件名：`imgs/00-cover-v2.png`

- 主标题：`5 个模型，1 张 GPU`
- 副标题：`小模型省钱，先让硬件共享起来`
- 画面中央是一张拟人化但保持技术感的 GPU 卡，五张不同颜色的小模型卡片通过一条共享队列接入 GPU。
- 五张模型卡用简洁图标区分：文档、实体、条款、照片、结论；不写长名称。
- 角落放一个小余机器人，拿着扳手或账单，强化「工程实践 + 成本」语义。
- 构图采用中轴聚合，中央正方形裁切仍需保留 `5 个模型`、`1 张 GPU` 和共享关系。

### 2. 理赔流水线：小模型多，服务也会变多

文件名：`imgs/01-pipeline-v2.png`

- 标题：`一单理赔，要走过 5 个模型`
- 从左到右的五步流程：`解析文档 → 抽取实体 → 重排条款 → 检查照片 → 生成结论`
- 每一步是一张独立的彩色手绘卡片，配单一图标，并用一条深蓝流水线串联。
- 在流程下方画出五个小服务盒子与各自占用的显存块，暗示「模型虽小，部署单元并没有自动变少」。
- 底部结论：`模型更小，不代表基础设施更省`

### 3. GPU 账单：付费时间与计算时间错位

文件名：`imgs/02-idle-gpu-v2.png`

- 标题：`GPU 账单按占用时间算`
- 上方是一条连续的「付费时间」长条；下方是零散的「真正计算」脉冲，中间大块空白标注为「等待」。
- 右侧放一张持续增长的账单，小余机器人看着账单和空闲 GPU，形成轻微反差。
- 用警示红圈出等待区，但避免整张图变成告警面板。
- 底部结论：`卡在等待，钱也在烧`

### 4. 部署收敛：五套服务合成一个入口

文件名：`imgs/04-one-server-v2.png`

- 标题：`五套服务，合成一个入口`
- 上半部分用五个分散的服务盒子表现旧方案，每个盒子都带队列、显存块和小型运维标记；整体以浅红叉号表示重复建设。
- 下半部分表现新方案：`Agent → 一个 API → 统一 Serving → 五类模型`。
- 一个共享调度器把请求分发到统一 GPU 池，五类模型仍可独立识别，但不再各自占一套服务。
- 底部结论：`共享硬件之前，先共享调度`

### 5. 共享资源池：显存跟着流量走

文件名：`imgs/05-sie-pool-v2.png`

- 标题：`共享资源池如何省 GPU`
- 中央为一个可视化 GPU 资源池，周围以环形或辐射结构放置五个机制：
  - `按需加载`
  - `LRU 驱逐`
  - `共享队列`
  - `按成本组批`
  - `弹性扩缩`
- 箭头需要表达模型进入、暂存、淘汰和批处理的方向，不把五个词做成毫无关系的装饰卡片。
- 用不同尺寸的显存积木表现资源可被重新组合。
- 底部结论：`显存跟着流量走`

### 6. 决策清单：什么时候值得换 Serving

文件名：`imgs/06-decision-checklist-v2.png`

- 标题：`什么时候值得换 Serving`
- 不再复刻 README 截图，改成一张工程决策卡。
- 左侧列出值得做 PoC 的信号：
  - `3 个以上模型`
  - `显存长期固定占用`
  - `各模型峰值错开`
  - `新模型就要新 Server`
  - `看不到等待时间`
- 右侧给出两条清楚的出口：
  - 命中多个信号：`用真实流量做 PoC`
  - 信号不明显：`先保留 vLLM / TEI`
- 中央可用小余机器人拿着检查板，引导视线从问题信号流向决策。
- 底部结论：`先测一周真实流量，再决定迁移`

## 生成与替换策略

1. 六张图片全部从零生成，不在第一版中文图上继续修补，避免继承低质量构图和字体。
2. 每张图单独生成，使用上述统一视觉系统和对应信息结构；封面与正文图分别控制比例。
3. 新图统一使用 `-v2.png` 文件名，保留现有图片作为回退版本。
4. 逐张检查尺寸、中文、构图、技术关系和缩略图可读性；不合格时只重做对应图片。
5. 六张图全部通过后，再把 `article-anti-ai.md` 的六处图片引用切换到 V2 文件。

## 验收标准

### 视觉验收

- 六张图在背景、线条、配色、字体气质、卡片样式和底部结论条上看起来属于同一套作品。
- 正文图缩小到手机宽度后，标题、核心关系和底部结论仍能识别。
- 封面按正方形裁切时，仍能看到「5 个模型」「1 张 GPU」和共享意图。
- 所有指定中文逐字正确，无乱码、异体字、错别字或无意义英文。
- 流程箭头、调度关系、等待时间和资源池机制在工程含义上成立。

### 文件与文章验收

- 六个 V2 文件存在且比例正确。
- `article-anti-ai.md` 中恰好引用六张 V2 图片，旧中文图片引用为零。
- 第一版中文图和英文原图仍保留在 `imgs/` 中。
- 文章正文、标题、摘要、作者和原有 frontmatter 不因换图被意外修改。

### 微信草稿验收

- 发布前预检识别到六张本地图片，封面采用 `00-cover-v2.png`。
- 通过 API 更新既有 `media_id`，不创建第二份草稿。
- 更新结果必须返回 `success: true` 和 `updated: true`。
- 回读原草稿后确认正文图片数为六，封面、标题和正文内容均正确。

## 回退方案

如果任意图片在微信端压缩后出现文字不可读、裁切失真或色彩异常，先停止更新并保留当前远程草稿。只修复问题图片，重新完成全套预检后再更新；由于旧图未删除，可随时把 Markdown 引用恢复到上一版本。
