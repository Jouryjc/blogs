先说结论

这篇论文最值得看的一点，不是又提出了一个新的 Agent Memory 方法。

它真正有用的地方，是把当前主流的 Agent 记忆系统拆成了四个可比较的模块：

  1. 信息怎么提取
  2. 记忆怎么管理
  3. 记忆怎么存储
  4. 信息怎么检索

然后，作者把 10 个代表性方法放进同一个实验框架里，在 LOCOMO 和 LONGMEMEVAL 两个长期记忆 benchmark 上横向比较。

最后得到的结论很务实：

Agent 记忆不是把历史对话塞进向量库就结束了，也不是越依赖 LLM 自动管理越高级。真正有效的记忆系统，需要层次结构、原始证据、关联关系和可控的管理策略同时存在。

如果你正在做长期对话、个人助手、代码 Agent、企业知识助手，这篇论文比单独看某个记忆框架更有参考价值。因为它讨论的不是“某个方法多厉害”，而是“记忆系统到底该怎么拆、怎么测、怎么取舍”。

为什么 Agent 记忆值得单独研究？

LLM 本身是无状态的。

每次调用模型时，模型只看到当前 prompt 里出现的内容。所谓“记得之前说过什么”，本质上是系统把历史上下文重新塞给模型。

这种做法在短对话里够用，但在 Agent 场景里很快会出问题。

比如一个长期运行的个人助手，需要记住用户的偏好、项目背景、历史决策、已完成动作和最近变更。一个代码 Agent，需要记住仓库结构、之前踩过的坑、测试失败原因和用户的长期偏好。一个科研 Agent，需要在多轮探索里积累证据，而不是每次重新开始。

这类任务有一个共同点：历史信息不只是聊天记录，而是下一步行动的依据。

所以，记忆系统要解决的不只是“存下来”，还要解决三个更难的问题：

  • • 怎么从长历史里保留有用信息
  • • 怎么在新旧信息冲突时更新记忆
  • • 怎么在回答问题时找回正确证据

这也是论文把 Agent Memory 当成一个独立系统来研究的原因。

论文给出的四模块框架

作者把现有 Agent 记忆系统拆成四个阶段。这个拆法很适合工程落地，因为它能帮我们判断一个方案到底强在哪里、弱在哪里。

模块要解决的问题常见做法
信息提取从当前消息里抽什么原文归档、摘要提取、图谱三元组抽取
记忆管理新旧记忆怎么合并和更新连接、整合、层级迁移、更新、过滤
记忆存储记忆以什么结构保存扁平存储、层次存储、向量存储、图存储
信息检索查询时怎么找回记忆关键词检索、向量检索、结构检索、LLM 辅助检索

这个框架看起来简单，但价值很大。

很多记忆方案表面上名字不同，实际上是在这四个模块里选择了不同组合。比如有的方案重视图谱抽取，有的方案重视分层存储，有的方案把 LLM 当成“操作系统”，让它自己决定该合并、更新还是删除记忆。

拆开以后，就能避免一个常见误区：只看最终分数，不知道分数来自哪个模块。

信息提取：别急着把原文丢掉

论文把信息提取分成三类。

第一类是直接归档，也就是把原始消息和时间戳存下来。这种方法最朴素，但有一个重要优点：不会丢细节。

第二类是摘要式提取。系统用 LLM 从一段对话里提炼关键词、主题、标签或简短摘要。它能减少冗余，但也可能把细节压没。

第三类是图谱式提取。系统从文本里抽实体和关系，变成类似“主体-关系-客体”的三元组。它适合做关系推理，但抽取错误或信息损失会影响后续回答。

这部分最值得注意的是一个反直觉结论：

结构化不等于信息更完整。

比如 Mem0 的图谱版本 Mem0^g 在一些任务上并不总是优于普通 Mem0。一个合理解释是，纯三元组会压掉原始对话里的语气、上下文和细粒度事实。对长期记忆来说，结构很重要，但原始证据同样重要。

更稳的做法不是“抽完结构就扔掉原文”，而是让结构化信息负责组织，原始片段负责兜底。

记忆管理：难点不是存，而是更新

记忆管理决定了系统如何维护一份“活的记忆”。

论文总结了五类操作：

  • • 连接相关经历：把语义相近、时间相近或上下文相关的记忆连起来
  • • 整合碎片信息：把重复或零散内容压缩成摘要、主题或用户画像
  • • 跨层级迁移：把短期记忆逐步转成中期、长期记忆
  • • 更新已有记忆：处理新旧事实冲突，保持记忆一致
  • • 过滤过时内容：删除、降权或标记不再有效的信息

这里有一个工程上很常见的取舍。

把记忆管理交给 LLM，看起来更灵活。比如让 LLM 自己决定什么时候合并、什么时候更新、什么时候调用工具。问题是，当记忆规模变大以后，LLM 要处理的不只是文本内容，还要处理工具调用、索引位置、冲突判断和状态维护。

这会让系统变得不稳定。

论文在上下文扩展实验里也观察到类似现象：像 MemOS、MemGPT 这类更接近 “LLM-as-OS” 的方案，在规模扩到 200% 时，更容易受到候选空间变大、工具调用复杂、索引冲突的影响。相反，MemoryOS 用更明确的规则式分层管理，稳定性更好。

这不是说 LLM 不能参与记忆管理，而是说：越底层、越频繁、越影响一致性的操作，越应该有确定性的系统设计托底。

存储结构：层次结构通常更占优

论文把存储结构从两个维度看。

一个维度是组织方式：扁平存储还是层次存储。

扁平存储很好理解，就是所有记忆放在同一层，比如一个 JSON 文件、一个 FIFO 队列、一个统一向量库。它实现简单，但随着记忆变多，检索噪声也会变大。

层次存储会把记忆分层。比如短期记忆保存最近上下文，中期记忆保存主题摘要，长期记忆保存稳定偏好或重要事实。

另一个维度是表示方式：向量还是图。

向量适合语义相似度检索。图适合关系、层级和多跳推理。两者不是替代关系，而是分工不同。

实验里，树结构和层次结构表现很突出：

  • • 在 LONGMEMEVAL 的 7B 模型设置下，MemTree 拿到最高 Overall F1：36.92
  • • 在 LOCOMO 上，MemOS 在 7B 和 72B 下分别拿到最高 Overall F1：37.05 和 42.79
  • • 在 LONGMEMEVAL 的 72B 设置下，MemoryOS 拿到最高 Overall F1：46.04

这些数字背后的共同点是：它们都不是单层向量库。

树结构和分层结构能同时保留两个东西：上层的概括信息，以及下层的原始细节。检索时可以先定位大范围，再下钻到具体证据。这比在一个巨大扁平空间里直接找 top-k 更稳。

检索机制：相似度不是推理

论文把检索分成四种。

关键词检索适合精确名字、术语和短语。向量检索适合同义表达和语义接近。结构检索适合沿着图或树做扩展。LLM 辅助检索适合把模糊问题改写成更明确的查询，或者识别查询里的关键实体。

很多 Agent 记忆系统的问题，不是没有检索，而是只会做一种检索。

比如向量检索能找到“语义接近”的片段，但它不天然知道两个事实之间的关系。用户问“我上次提到的那个项目后来换负责人了吗”，系统可能需要跨多个会话，把项目、负责人、时间更新和当前问题串起来。

这不是单纯相似度能解决的。

所以论文强调，记忆系统要能建立显式或隐式连接。实验里也能看到，缺少关联操作的方法，比如 MemoryBank、MemGPT、MemoChat，在 LONGMEMEVAL 的 Multi-Session 和 LOCOMO 的 Multi-Hop 任务上表现偏弱。

换句话说，长期记忆不是一个“更长的搜索框”，而是一个能保存关系和版本的系统。

实验怎么做？

作者评测了 10 个代表性 Agent Memory 方法，包括 A-MEM、MemoryBank、MemGPT、Mem0、Mem0^g、MemoChat、Zep、MemTree、MemoryOS、MemOS。

评测数据集主要是两个：

LOCOMO：长期人类对话问答任务。每段对话平均 27.2 个 session、约 588.2 轮对话，问题类型包括单跳检索、多跳检索、时间推理和开放域知识。

LONGMEMEVAL：长期用户-AI 交互记忆评测。包含 500 个高质量问题，每个问题对应平均 50.2 个 session、约 115,000 tokens 的历史上下文，评估信息提取、多会话推理、知识更新和时间推理。

实验指标用 F1 和 BLEU-1。默认主干模型是 Qwen2.5-7B-Instruct，同时也比较了 Qwen2.5-72B-Instruct、LLaMA3.1-8B 和 GPT-4o-mini。

实现上，作者把方法放到统一框架下重实现，并使用统一的 embedding 模型 all-MiniLM-L6-v2。这个设置不完美，但它的好处是减少了“每个方法各测各的”带来的比较偏差。

第一个结论：强模型仍然很重要

记忆系统能帮 Agent 找回历史信息，但它不能完全替代模型的推理能力。

论文里一个明显现象是，时间推理任务很依赖主干模型规模。比如在 LOCOMO 上，MemoryOS 和 MemoChat 从 Qwen2.5-7B 换到 Qwen2.5-72B 后，时间推理表现出现超过 2 倍的提升。

这说明一件事：把证据找回来只是第一步，模型还要能理解“先后关系”“更新关系”“当前有效事实”。

如果系统只靠最后一步的 in-context reasoning 来处理时间问题，那么模型越弱，越容易错。更稳的方向是把时间信息变成结构化能力，比如显式时间戳、版本记录、失效标记和时间检索算子，而不是完全交给 LLM 临场发挥。

第二个结论：高分通常要花更多 token，但架构决定性价比

论文还专门分析了 token 成本。

整体上，高性能方法往往消耗更多 token。这并不奇怪，因为更复杂的记忆管理、摘要、更新和检索都可能调用 LLM。

但更有用的结论是：成本不只由“用了多少 LLM”决定，更由记忆架构决定。

比如 MemTree 和 MemOS 准确率高，但 token 开销也大。MemoryOS 的表现不一定每项第一，但在效果和 token 成本之间更均衡。MemoChat、MemoryBank 这类简单方法 token 成本低，可是准确率也上不去。

论文还指出一个很实用的优化方向：调整信息处理粒度。

如果每一轮对话都单独抽取、更新和插入，成本会随着会话增长快速上升。更合理的做法是把多个 dialogue turns 作为一个片段来处理。MemoryOS 会把对话组织成 segment 再进入中期记忆，MemoryBank 也有按天汇总的思路。

这意味着，记忆系统不一定要“越细越好”。太细会让索引膨胀、更新昂贵、检索噪声变大。适当粗粒度反而可能在成本和效果之间取得更好的平衡。

第三个结论：上下文越大，噪声越难压住

作者用 LONGMEMEVAL 构造了不同上下文规模：50%、100%、150%、200%。

结果很符合直觉：随着上下文规模从 50% 扩到 200%，几乎所有记忆架构的 F1 都会下降。

原因不是模型突然变笨了，而是检索空间变大以后，相关信息和无关信息混在一起，信噪比下降。

知识更新任务尤其敏感。

因为知识更新要判断“最新事实是什么”。当历史里存在多个互相冲突的旧版本时，记忆越多，过时信息越容易干扰检索。比如用户过去说自己住在上海，后来搬到深圳，再后来又改到杭州。系统需要知道当前答案是杭州，而不是从历史里随便召回一个城市。

时间推理相对稳定一些。因为时间关系有更明确的顺序线索，“之前”“之后”“最近一次”这类关系不完全依赖语义相似度。

这个实验给工程实践的提醒是：不要只测小上下文。一个记忆系统在 10 条历史上表现好，不代表它在 1000 条历史上还能稳定。

第四个结论：记忆系统普遍有近因偏差

论文还做了一个位置敏感性实验。

作者把关键证据分别放到上下文的早期、中期和后期，看系统能不能稳定找回。

结果是，大多数方法更擅长找后期证据，也就是更近的信息。

这不难理解。越早出现的证据，后面经过的对话越多，干扰越多，也更容易在摘要、更新或检索排序中被冲淡。

论文给了几个数字：

  • • MemTree 的 Overall F1 从 Early 的 34.13 提升到 Late 的 37.37
  • • MemOS 的 Overall F1 从 Early 的 29.10 提升到 Late 的 34.40
  • • MemoryOS 的 Late-Early 差距较小，只有 +1.29 F1

这里的关键不是“最近的信息更重要”，而是系统不应该无意识地偏向最近信息。

有些任务确实需要近因偏好，比如用户刚刚改了地址。但有些任务需要准确回忆旧事实，比如“我第一次提到这个项目时的目标是什么”。如果系统没有版本管理和证据保留机制，就会把这两类任务混在一起。

论文还发现，短暂的、会话局部的信息更容易受位置影响；长期偏好相对稳定。这个结论也符合经验：用户一时说过的细节容易被冲掉，但长期偏好如果被多次提炼，反而不太受证据位置影响。

作者的新方法：把树结构和三层记忆组合起来

基于上面的分析，作者设计了一个新的记忆方法。

这个方法并不是从零发明一套新概念，而是把已有方法里表现好的模块组合起来：

  • • 借鉴 MemTree、MemOS 的树状组织
  • • 借鉴 MemoryOS 的短期、中期、长期分层
  • • 用更粗粒度的 segment 降低 token 成本
  • • 从多个层级独立检索，再合并上下文

它的工作流可以简单理解成这样：

新消息进入短期记忆
        ↓
短期记忆满了以后，最旧的一部分按语义切成片段
        ↓
片段进入中期记忆树，叶子节点保留片段摘要，父节点保存聚合摘要
        ↓
经常被访问、最近还重要的片段，通过 heat score 晋升到长期记忆
        ↓
查询时同时检索短期、中期、长期记忆，再交给 LLM 生成答案

这个设计的好处是比较清楚的。

短期记忆保证当前上下文连续，中期记忆用树结构承接主题和片段，长期记忆保存高价值内容。检索时，短期记忆可以全量带上，中期记忆同时做向量检索和树上的 beam search，长期记忆再做向量检索。

它不是把所有信息都塞进一个库里，而是承认不同记忆有不同生命周期。

新方法效果如何？

在 LONGMEMEVAL 上，作者的新方法 Overall F1 是 38.79。相比最强现有 baseline MemTree 的 36.92，整体相对提升 5.17%。

在 LOCOMO 上，新方法也拿到最好 Overall：

  • • Qwen2.5-7B：38.03
  • • Qwen2.5-72B：43.87

同时，它的平均 token 开销低于每段对话 450 tokens。这个数字很重要，因为很多记忆方法不是效果不行，而是效果一上来，成本也跟着爆。

不过也要注意，作者的新方法不是每个子任务都第一。

比如 LOCOMO 里，MemOS 在一些复杂任务上仍然很强，尤其是多跳检索和时间推理。GPT-4o-mini 设置下，MemOS 的 Overall F1 也略高于作者方法。作者方法的优势更像是：整体分数高，成本低，跨模型表现稳定。

这才是工程上更有意义的胜利。

真实系统里，我们通常不需要一个在单个子任务上极限刷分的方法，而需要一个不太贵、不太脆、规模变大以后还能工作的记忆架构。

这篇论文对做 Agent 的人有什么启发？

第一，先搭层次结构，再考虑复杂智能管理。

很多团队一上来就想让 LLM 自动决定记忆怎么写、怎么合并、怎么删。这个方向有吸引力，但也容易把系统变成黑箱。更稳的起点是短期、中期、长期分层，再给每层定义清楚的迁移规则。

第二，保留原始证据。

摘要、标签、三元组、embedding 都是索引，不是事实本身。只保留加工后的记忆，会在需要细节时出问题。结构化信息负责提速，原始片段负责校验。

第三，给记忆加版本意识。

长期 Agent 一定会遇到知识更新。用户偏好会变，项目状态会变，组织关系会变。如果只是覆盖旧记忆，未来就无法解释答案来源；如果只是追加新记忆，检索又会被旧版本污染。

更好的做法是保留历史，同时标注有效期、更新时间、置信度或失效状态。

第四，评测时要看成本、规模和位置。

只测准确率不够。记忆系统还要测 token 成本、上下文扩大后的衰减、早期证据能不能找回、换主干模型后是否稳定。否则 Demo 里表现好的系统，生产里可能很快变慢、变贵、变不准。

最后

这篇论文给 Agent Memory 做了一次比较系统的“拆机评测”。

它没有把记忆讲成一个玄学能力，而是拆成工程模块：提取、管理、存储、检索。这个视角很重要，因为 Agent 记忆最终不是一个 prompt 技巧，而是一套长期运行的数据系统。

如果把这篇论文压成一句工程建议：

先用层次结构管理记忆生命周期，用结构化索引提高检索效率，用原始证据保证可追溯，再让 LLM 参与那些真正需要语义判断的环节。

Agent 记忆的下一步，不是无限扩大上下文，也不是把所有东西交给模型自己管。

更可靠的方向，是把“记住什么、怎么更新、如何找回、何时失效”变成明确的系统设计。
